# Auditoría de seguridad — Orientador Vocacional UPB

Revisión de la rama `main` (backend Spring Boot + frontend HTML/JS + Supabase). Cada hallazgo indica severidad, ubicación, riesgo y la corrección aplicada en la rama `devin`.

Severidades: **Crítica** · **Alta** · **Media** · **Baja**.

## Acciones manuales que el equipo DEBE hacer (no se pueden resolver con código)

1. **Cambiar la contraseña de la base de datos de Supabase** (Project Settings → Database → Reset database password) y **rotar la clave pública de Supabase** (Project Settings → API Keys). Las credenciales reales están en el historial de git (ver H-01). Borrar el archivo no basta: cualquiera que tenga una copia del repositorio puede verlas.
2. **Ejecutar `proyecto-registro/sql/seguridad_rls.sql`** en el SQL Editor de Supabase (ver H-03).
3. Configurar las credenciales nuevas como **variables de entorno** (ver `application.properties.example`).
4. Opcional (recomendado): limpiar el historial de git con `git filter-repo` o BFG para eliminar `application.properties` de los commits antiguos. Esto reescribe el historial de `main` y obliga a todos a volver a clonar, por eso no se hizo automáticamente.
5. En Supabase → Authentication: activar la confirmación de correo y la protección contra contraseñas filtradas ("Leaked password protection").
6. En producción, servir la app solo por **HTTPS**.

## Hallazgos

| ID | Severidad | Hallazgo | Ubicación | Corrección |
|----|-----------|----------|-----------|------------|
| H-01 | Crítica | **Credenciales expuestas en el repositorio.** `application.properties` se subió con la URL y la clave pública de Supabase (commits `d820a34`, `cd4d181`, `8562a6c`) y, en el commit `8562a6c`, también con el usuario y la **contraseña de PostgreSQL**. Siguen en el historial aunque luego se agregó al `.gitignore`. Con la contraseña cualquiera puede leer, modificar o borrar toda la base de datos. | Historial de git | Plantilla `application.properties.example` que lee todo de variables de entorno (`${DB_PASSWORD}`, etc.); `.gitignore` ampliado (`.env`, `*.key`, `application-*.properties`). **Requiere rotar las credenciales (acción 1).** |
| H-02 | Crítica | **Sin autenticación en el backend / IDOR.** El servidor nunca verificaba el token de sesión. `POST /api/test/resultado` recibía el `usuarioId` en el cuerpo y `GET /api/perfil/historial?usuarioId=` lo recibía por URL: cualquiera podía leer el historial de otra persona o guardar resultados a nombre de otro usuario solo cambiando el id. El "login obligatorio" existía únicamente en el navegador (`requerirSesion()`), y se salta llamando a la API directamente. | `TestController`, `PerfilController`, `js/test.js`, `js/perfil.js` | Nuevo `InterceptorAutenticacion`: exige `Authorization: Bearer <token>` en `/api/test/resultado`, `/api/perfil/**` y `/api/carreras/recomendadas`, y valida el token contra Supabase (`/auth/v1/user`, con caché de 60 s que guarda solo el hash SHA-256 del token). Los controladores toman el id **del token validado**; se eliminó `usuarioId` de las peticiones. El frontend usa `fetchAutenticado()`. |
| H-03 | Alta | **Tablas posiblemente expuestas por la API REST de Supabase.** La clave pública y la URL (filtradas en H-01) permiten consultar las tablas por PostgREST si no tienen RLS. ## Riesgos aceptados / pendientes

- **Enumeración de correos en el registro:** responder "correo ya registrado" lo exige el criterio CA-02 de la Historia 1. El límite de intentos (H-08) reduce el abuso.
- **Token en `localStorage`:** es accesible para JavaScript si hubiera un XSS. Se mitiga con H-04 y la CSP de H-07. La alternativa (cookie `HttpOnly` + protección CSRF) implica rediseñar la sesión.
- **`/api/perfil/resumen` y `/api/carreras/recomendadas`** calculan a partir de la afinidad que envía el cliente; un usuario podría manipular *su propia* vista, pero no la de otros ni lo guardado en la BD (eso lo calcula el servidor en `/api/test/resultado`).
- **Cerrar sesión** borra la sesión local; el token de Supabase sigue siendo válido hasta que expira (máx. 1 h por defecto).
- El limitador de intentos es en memoria (una sola instancia del servidor).
